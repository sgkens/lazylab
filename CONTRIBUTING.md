# Contributing to lazylab

How to set up lazylab from source, the checks a change must pass, and the conventions for branches, commits, code and documentation.

## Before you start

- Open an issue first for anything larger than a fix, so the approach can be agreed before you write it. lazylab is built for one owner on their own machine; [What it is not](docs/src/index.md#what-it-is-not) lists features that are out of scope.
- Open work and known gaps are tracked in [devtracker-pending.md](devtracker-pending.md). Task ids such as `ENV-5` or `SEC-9` are stable; mention one in your merge request when it applies.

## Set up

Requires Bun 1.3 or later. Shell: bash, repository root.

```bash
git clone https://gitlab.com/sgkens/lazylab.git && cd lazylab
bun install
bun run dev          # API + Vite with reload, http://127.0.0.1:3000
```

Without a GitLab profile the server runs on demo data, which is enough for most UI and API work. Tests and the dev server keep their data in `.data/` (ignored by git); `bun test` uses a temporary directory instead.

## Checks

Every merge request must pass these. Shell: bash, repository root.

```bash
bun run lint                     # tsc --noEmit over server, client and CLI
bun test                         # unit tests
bun run build                    # the SPA still builds
cd docs && bun install && bun run build   # when docs/ changed
```

For changes to a flow that reaches GitLab, also run it end to end in demo mode, and say in the merge request what was and was not verified against a live GitLab instance.

## Branches and commits

- Branch from `develop` with a descriptive name (`feature/env-pull-run`, `fix/variables-pagination`). `main` stays stable.
- Use [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): summary`, with `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `ci`. Write the summary in the imperative.
- Add `build: major|minor|patch` to the body when the change affects the version.
- Group commits by logical change: server, UI, CLI, docs and tracker updates are usually separate commits.

## Code

- Match the surrounding code: naming, comment density and idiom. The server is Express on Bun, the UI is React 19 with Tailwind 4, and the CLI is plain TypeScript run by Bun.
- Keep decisions in pure functions with unit tests (`evaluateWatch`, `resolveEnv`, `dueWarnings` are examples), and keep I/O at the edges.
- Report failures. Do not catch an error and return an empty list or made-up data; the UI shows what failed and why.
- Every control in the UI must reach a real GitLab call or say what it cannot do. Demo data stays behind the demo path.
- Treat secrets carefully: masked values never go to the browser in lists, agent-facing tools that return secrets need a token with secret access, and nothing secret is logged.
- CLI output computes layout on plain text and applies colour last (see `cli/ui.ts`).

## Documentation

- User-facing changes update the documentation site in `docs/src/` in the same merge request. New pages must be added to `docs/src/_data/nav.js`.
- Start each page with a one-sentence `abstract`, use H2 and H3 only, and state the execution context of every code block (`# Shell: bash, repository root`).
- Update [Feature status](docs/src/reference/status.md) when something is verified, or newly unverified, against a live GitLab instance.
- Plain language: no marketing words, no emojis.

## Brand assets

Logos, icons and colour tokens are generated by `brandkit/build.mjs`. Edit the script, never the generated files, then run `bun run build` in `brandkit/`; it refreshes the copies in `src/assets/brand/` and `docs/src/assets/brand/`. See [brandkit/README.md](brandkit/README.md).

## Security issues

Do not open a public issue for a vulnerability. See [SECURITY.md](SECURITY.md).
